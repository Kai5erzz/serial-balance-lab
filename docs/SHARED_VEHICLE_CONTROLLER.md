# 实车共用 C 控制器和仿真接入

RL-lab 的原始对照入口直接运行 code_914 当前工作区的 C 控制代码。底盘的正常平衡、行驶、转向、小陀螺、跳跃、离地与落地、自起身、磕台阶、观测器和电机限幅，以及云台 yaw 控制，都由 C 文件执行。Python 负责物理模型、传感器和执行器接口、显示与记录。

2026-10-15 按用户要求，`run_operator.py` 默认使用独立的 `jump46` 仿真配置。它在临时副本上应用 `firmware/profiles/jump46.patch`，保留单髋 40 N·m、总请求 160 N·m 的 46 cm 档，并修正行进跳跃的倾角偏置和落地交接。后续还加入了仿真磕台阶档的速度、接触及交接调整，具体通过项与限制见 [低台阶及窗口检查](NATIVE_BUMP_AUDIT_20261015.md)。当前磕台阶接近腿长目标加高至 **32 cm**，退出时连续缓降；部分斜向改善，−3° 对照退步，慢速和实际 20 cm 路沿仍失败，见 [加高实测](NATIVE_BUMP_TALLER_20261015.md)。**不会修改 code_914 源码或 `firmware/vehicle/` 镜像。** 使用 `--controller-profile source` 可运行原始对照。`VehicleRuntime()` 和 `VehicleSimulation()` 默认仍为原始对照；程序调用可显式传入 `profile="jump46"` 或 `controller_profile="jump46"`。

这完成了控制代码与参数的共用。当前物理试验仍未通过稳定站立和自起身验收，因此第一阶段的实车物理对应尚未完成；旧 Python 控制器的行为通过不能用作这条共用 C 控制链的行为通过。

## 时钟和电机接口

主机从实车 `main.c`、`tim.c`、HAL 时钟配置和 FreeRTOS 配置推导节拍，并校验任务内外层的延时调用、优先级和创建顺序。当前底盘、指令、云台、INS 和 DJI 为 1 ms；TIM4 每 2 ms 调用共用的 `dm_controll_all_poll`。普通驾驶保留 LB、LF、RB、RF、yaw 轮询，各电机约每 10 ms 发一包；主动跳跃及其落地恢复改为每个 TIM4 周期发送完整一组。原有报文编码、回调与力矩预算继续生效。正常控制历史 5 ms 时间常数保留，跳跃局部测速使用实际反馈时间戳。

桌面按 `rm_task.h` 的同优先级任务创建顺序运行 INS、电机、底盘、指令、云台。底盘下一拍才读到本拍的新指令，DJI 发送上一拍的底盘结果；输出记录的 mode 来自底盘实际执行状态。TIM4 在本拍任务之后执行。该顺序是名义调度假设，任务创建顺序不能证明实车运行时的精确相位，仍需测量抢占、中断和总线到达时刻。

电机输出先经过原始驱动的限幅、整型转换和 CAN 打包，再解码给物理模型。DM 的位置、速度、Kp、Kd、力矩及命令保持均保留；零力矩的协议量化偏差也保留。轮电流到输出轴力矩的比例和气弹簧控制参数直接从编译后的 C 获取。

MuJoCo 的 DM 反馈在对应电机发包之后的下一拍到达；初始静态读取先填充所有电机。该 1 ms 回复延迟是明确的桌面调度假设，仍需用实车时序核对。DJI 与 BMI088 输入每 1 ms 更新。云台 IMU 由原始 INS 任务按 accel、gyro、Euler 轮询，再经过原始 CAN 解码，不将三种数据同时强制刷新。

原始 BMI088 驱动的板级读取边界被替换为理想的校正后传感器读数；姿态解算、安装修正、运动加速度滤波和发布均运行原始 C。当前传感器位于模型 base COM，未加入实测安装位置、噪声、偏置和总线抖动。云台只模拟 yaw，pitch 反馈固定在中心。

## 零位和坐标

零点来自用户指定的 `rl-serial-balance-jointpd/configs/calibration/encoder_zero_2026-09-13.json`，校验其三个配套证据文件。四个 CAD 零点与 RL-lab 原零位姿态文件一致：

| 关节 | CAD 零点 rad |
| --- | ---: |
| l_j1 | 0.8888879963997892 |
| l_j2 | 1.831365792476727 |
| r_j1 | -0.8601638293762661 |
| r_j2 | -1.802641625453204 |

硬件输入使用 `E = Q − Znew`，四个关节都不额外反号。输出力矩与对应 CAD 关节轴同号。DM ID 顺序为 LB=l_j1、RB=r_j1、RF=r_j2、LF=l_j2。云台 yaw 的电机角与 CAD yaw 同号，实车 `GIMBAL_YAW_DRIVE_SIGN` 的反向由原始控制器处理。

机体原始 IMU XYZ 对应侧向、前向、上向的右手系。原始 INS 代码负责 yaw、pitch、roll 和 gyro 的发布符号。坐标轴由保存的直立姿态确定，倒地重置不会把倾斜机体重新当作水平。

jointpd 的精确 CAD FK 锚点与 code_914 的 `DM_ZERO_OFFSET` 是两个不同的标定层，不能只替换零点后再把历史 Python 的 phi 补偿塞进 C 输入。当前接口保留真实 E 和原始 C offset。保存的旧站姿在原始 C 下有小量左右 phi0 偏差，自起身的 90° 分支选择可能受此影响，需要与当前固件的实测原始编码器一起核对。

```bash

```

默认使用已存在的 `identified_2026-09-21` 物理 profile。该 profile 只修改物理模型的摩擦、阻尼、惯量和质量，不能修改 C 控制器参数。需要原始 XML 对照时使用 `--plant nominal`；碰撞模型可用 `--variant full`，台阶场景可用 `--variant platform`。

图形入口启动时暂停。Space 运行或暂停，R 重置物理模型和 C 控制器状态并暂停，3 使用旧站立初始姿态，5 使用精确编码器零位初始姿态；1 松控，2 遥控，T 小陀螺，方向键控制行驶和 yaw，J 使用真实遥控跳跃请求。7 和 8 选择 LOW 与 MID；9 或 B 按实车左拨杆上位语义同时选择 HIGH 并请求磕台阶。控制器自行决定请求是否允许执行。`--mode open/follow/recovery` 是显式的命令注入诊断路径，默认 `remote` 经过原始 DR16 门控。

JSONL 保存固件和桌面硬件接口构建指纹、物理参数身份、精确零位、名义任务相位、每个控制拍的反馈、反馈到达掩码、命令、实际电机包输出，以及指定的原始 VOFA 页。重放使用一份新的 C 静态状态，逐项比较记录；输入从第一拍 1000 us 开始并连续，不能省略启动历史或通过跳拍伪造较低控制频率。固件或桌面接口构建变化时，默认比较明确拒绝旧记录。`Feedback.raw_imu=0` 允许导入已经发布的 INS 数据做控制链重放，默认物理试验使用 `raw_imu=1` 运行原始 INS。

物理接口检查 MuJoCo 的 BADQPOS、BADQVEL、BADQACC 警告和物理时钟连续性。数值异常后的自动重置会明确终止试验，不能因重置后数值有限就把控制历史判为有效。

## 验证结果和剩余工作

新增 14 项接口测试通过，覆盖源码清单、精确零位、VMC 几何、原始姿态积分、DM 轮询与命令保持、任务指令交接、实例隔离、时间连续性、yaw 双环与限幅、云台回中、遥控丢失、无效遥控帧、反馈保持和完整物理记录重放。当前调度下的 5000 拍自起身记录逐项重放一致。历史 Python 的九项回归全部通过；code_914 的六项相关生产逻辑检查和 STM32 编译通过。

`tools/validate_vehicle_trial.py` 的八个 5 s 原始 C 场景均保持数值有限，但稳定站立、自起身、行驶、yaw 跟随、小陀螺、跳跃和磕台阶尚未通过物理行为验收。站姿启动在 RECOVERY 中出现故障 42，即原始腿长估计低于保护下限；精确零位启动能推进到 LQR_HANDOFF，但末段仍有非轮部件触地、机体倾斜和站立确认缺失。后续请求受原始自起身门控，因此不能把这些场景的命令发出称为跳跃或台阶动作已通过。

快速模型的精确零位自起身在最后 1 s 出现约 15.35° pitch 峰值，双轮同时接触比例为 0.4%，非轮部件接触峰值约 1023 N，末帧轮电流达到 +8191/-8191。完整碰撞模型的同一 5 s 自起身也未通过，末帧 roll 约 75.70°；不能用简化碰撞解释全部失败。原始记录和报告在 `out/native/physical_trials/` 与 `out/native/full_collision/`，均包含控制与标定身份。

台阶场景已修复辨识参数加载器只接受 `ground`、遇到 `ground_outer` 就报错的问题，新增检查确认所有台阶层的摩擦均使用辨识值。相关 sysid 检查通过；台阶模型的 3 s 松控与自起身记录保持有限，自起身仍未通过，报告位于 `out/native/platform_collision/`。当前试验没有证明上台阶或落台阶动作通过。

进一步的 [摩擦排查](NATIVE_FRICTION_AUDIT_20261014.md) 完成 20 组快速模型和 6 组完整碰撞模型对照，25 组数值有效，全部未通过物理站立验收。当前实际地面接触滑动摩擦均为 1.2；condim=3 未启用接触扭转或滚动摩擦。用户确认底部阻力大、导轮几乎不滚动，继续保留固定底部接触近似。提高底部摩擦或轮轴阻尼可改变交接结果，但完整模型会出现确认后翻倒，不能据此采用新的默认参数。固件站立确认也不能代替物理接地和姿态验收。摩擦批次使用跳跃 roll 修正前的源码身份；报告在 `out/native/friction_audit/`，没有用新身份覆盖旧报告。

[极性排查](NATIVE_POLARITY_AUDIT_20261014.md) 的 37 个方向用例和 4 组模型/姿态几何检查通过。新增 6 组极性回归、14 项原控制接口回归，以及实车跳跃 roll 生产代码回归和普通 roll 范围检查通过。修正后复测默认 5 s 自起身，其 100 Hz 轨迹与修正前逐字节一致，仍未通过物理站立。这条跳跃分支的修正不能解释当前自起身失败；实车增益和默认物理 profile 保持原值。

后续 [轮子接管与 yaw 跟随方向排查](NATIVE_WHEEL_HANDOFF_AUDIT_20261014.md) 进一步限定了上述局部方向检查的结论：它们不能证明整车闭环方向正确。两轮输出力矩与反馈同时反号的诊断改善了快速和完整碰撞模型的接管姿态，却在 Follow 下反复加速到约 ±6.5 rad/s。IMU yaw 角度与角速度同向；原 Follow 外环期望的机械角变化方向与当前仿真相反。仅在回中完成后反号跟随角输入的 8 s 对照，末段 yaw 速度小于 0.006 rad/s、pitch/roll 小于 0.38°/0.21°，双轮全接地且无非轮接触。该不完整的角度接口反号只用于定位问题，尚未进入默认配置或实车 C；仍需建立可移植的一致轮轴、云台电机和传感器对应关系。

补充的 yaw 完整接口候选按实车配置的 1:1 反向齿轮，同时变换电机位置、速度、反馈/输出力矩，并按正世界方向输入云台 IMU，保持底盘 INS 和原 C 不变。零输入及正负云台命令三组快速模型 8 s 对照，末段 yaw 速度均低于 0.008 rad/s，双轮全接地且无非轮接触，正反跟随最终机械回中。该结果支持修正仿真对应关系而保留实车 Follow 增益；实车安装方向与整车行为验证未完成，候选尚未成为默认接口。

目前已辨认的物理对应差异包括：C 支撑质量 12.801 kg 与 identified 模型总质量 13.836367 kg 的区别；CAD FK 与固件 offset 的区别；实际 IMU 安装点与噪声缺省；反馈延迟、线程相位及总线抖动的简化；原 XML 云台 1.2 Nm 和 identified hip 20 Nm 的持续力矩范围与固件峰值命令范围的区别。新接口将物理输入范围放宽到原 DM 协议范围，由原始 C 决定命令限幅，仍需确认真实电机的峰值持续时间、速度力矩曲线和电气响应。

`~/sample` 的 25 个采样已建立只读目录清单，工具为 `tools/catalog_vehicle_samples.py`，包含文件摘要、时间间隔、丢样和候选页识别。现有源码文档证明部分采样属于历史固件，不能只按文件修改时间认定它们属于当前版本。诊断页可以对照轨迹和保护原因；它们缺少完整的原始 IMU、四髋编码器与反馈力矩、两轮原始反馈、yaw 反馈、遥控和反馈到达时间，不能还原每个 1 ms 的完整控制输入。

第一阶段剩余工作是按这些证据核对物理模型和传感器时序，再运行共用 C 控制链的站立、自起身、行驶、yaw、小陀螺、跳跃、落地和台阶行为验收。控制源码与物理标定分别保留身份，任何新的物理拟合只能修改 plant 与硬件接口；控制策略修改仍应同时进入实车源码和仿真。
