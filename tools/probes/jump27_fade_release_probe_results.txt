Finite 3-case probe for jump27/jump28 thrust fade and release hypotheses

Probe: jump27_fade_release_probe.py (runtime-only controller/model overrides)
Model: rl-lab whole_body_lqr_fast.xml; one fixed stand/jump run per case at 1 ms.
Controller setup: 35 N.m hip actuator bounds; current firmware 28 N.m airborne VMC hip limit; normal-mode theta guard remains inactive during the jump; powered-grounded THRUST differential theta D uses the same timestamped observer as v3; jump length-rate consumers use the timestamped observer; the main length PID retains its own measured 1 ms derivative path. Physical contact remains simulator-detected; delayed software takeoff confirmation remains at 0.32 s. The stroke-release variant changes only the thrust release time and uses the actual release time as the profile-prestart origin. It does not force flight or edit the no-takeoff fallback.

All three runs returned to idle with double contact. None requested or applied hip torque above 35 N.m. Identical results are expected here: the model's mean leg length never reached the real-log threshold, so neither the no-rearm latch nor early stroke release activated. This run does not test whether disabling the real robot's observed re-arm improves attitude or preserves launch height. The model still produces about 0.016 rad maximum powered-THRUST leg-angle difference, far below jump28's observed 0.5814 rad in THRUST and 0.6156 rad in sampled FLIGHT, so its stable landing is not evidence of real-robot safety.

Real-log motivation: in jump28, while state=THRUST, off-ground=0 and timer bit=1, mean leg length was 0.367/0.375 m at elapsed 0.180/0.190 s (recomputed fade scale 0), then fell to 0.354 m at 0.210 s (scale 0.058; 4.1 N extra boost), 0.339 m at 0.220 s (15.0 N), and 0.323 m at 0.230 s (25.8 N). Software raw-support candidates reappeared asymmetrically at 13.6/0.3 N, 32.8/18.6 N, and 52.9/35.7 N. There is a logger gap from elapsed 0.260 to 0.320 s. At 0.320 s the timer was off, air-profile was on, off-ground remained 0, raw candidates were zero and final support commands were -19.4/-120.9 N. This proves software command re-arming under the current travel-fade formula; the log cannot confirm physical contact or delivered ground force. jump26 has the same extension-then-retraction pattern in both complete THRUST records.

Interpretation: latching the fade to zero after first target reach is the cleanest first firmware experiment because it removes only the re-arm while preserving the original timer and prestart path. Stroke release at first full extension is a larger change: it can begin pre-tuck while software still sees ground, changing both launch impulse and contact transition timing. If tested, compare physical contact, software off-ground, release origin, support commands, apex, and touchdown attitude separately. Do not treat this simulator run as validation.
